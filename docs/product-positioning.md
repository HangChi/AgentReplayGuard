# AgentReplayGuard 产品定位

**版本**：0.14.0（已发布）
**日期**：2026-11-14
**状态**：已发布（PyPI 首个正式版本；13 个特性规格全部实现）
**关联规格**：[spec.md](../specs/001-effect-safety-testing/spec.md)

## 1. 一句话定位

AgentReplayGuard 是面向 **LangGraph + pytest** 的副作用安全测试工具：用确定性故障注入和
effect 账本，验证重试、Checkpoint 恢复与 Interrupt 重放不会重复执行支付、退款、写入、通知
等业务操作。

它回答一个非常具体的问题：**当 Agent 工作流被重试或恢复时，同一笔业务操作会不会被执行两次？**

## 2. 问题与技术价值

AI Agent 调用有副作用的工具时，失败语义与普通函数调用不同：

1. 服务端已提交（如退款成功），但响应丢失，Agent 认为失败并重试。
2. LangGraph 的 durability 保证的是图状态恢复，不保证外部副作用 exactly-once（issue #9240）。
3. 长时间 tool call 可能在恢复时被静默重执行（issue #7417）。
4. interrupt 恢复会从头重跑节点，放在 interrupt 之前的副作用可能再次执行。
5. 传统单元测试用 mock 验证「调用了几次」，但无法表达「服务端提交了几次」；可观测平台能
   看到调用，却不能判定业务上是否重复。

技术价值在于把「业务副作用的最终一致性」变成可在 CI 中断言的属性：记录每次 effect 尝试、
区分提交状态、按业务键聚合，并用不变量判定重复。这层能力现有 mock、录制回放和 APM 工具
都不直接提供。

## 3. 目标用户

### 3.1 P0 用户（MVP 只服务这一类）

- Python 后端工程师，用 LangGraph 构建包含资金、订单、通知类工具的串行工作流。
- 已经在写 pytest，习惯用测试守护行为，而不是只看日志。
- 对「重试会不会重复退款/重复扣款」有真实担忧，或已经遇到过一次疑似事故。
- 能接受在测试中显式声明业务键和故障场景，愿意为可靠性写少量测试代码。

### 3.2 非目标用户（MVP 明确不服务）

- 只做 LLM 输出质量评估的团队（应使用 DeepEval / promptfoo 等）。
- 需要生产环境监控、告警、全链路追踪的 SRE 团队（应使用 Langfuse / Phoenix 等）。
- 需要录制生产流量并回放的团队（应使用 AgentTape / agent-vcr 等）。
- 不写测试、希望工具自动修复幂等性的团队。

## 4. 差异化定位

Phase 0 核实过的邻近项目及差异：

| 类型 | 代表项目 | 它们擅长 | AgentReplayGuard 的不同 |
|------|----------|----------|--------------------------|
| Agent 混沌测试 | Flakestorm、BalaganAgent | 故障注入、输出契约 | 聚焦「副作用多重性」断言；BalaganAgent 的 LangGraph 支持仍在路线图 |
| 录制/回放 | AgentTape、agent-vcr、Chronicle | 捕获并重放调用 | 回放通常屏蔽副作用；本工具保留副作用并检查是否重复提交 |
| 可观测/评测 | Langfuse、Phoenix、DeepEval、promptfoo | 追踪、评估、数据集 | 不做质量评估，只做可复现的副作用安全测试 |
| 通用故障代理 | Toxiproxy、Jepsen | 网络故障、分布式一致性 | 面向单进程 LangGraph 场景，无需真实网络与服务部署 |
| 工作流持久化 | Temporal、Restate、DBOS、Inngest | 提供 exactly-once 语义 | 不替换运行时，只验证用户现有实现是否安全 |

核心差异点：**Effect 多重性断言 + LangGraph 原生恢复场景 + pytest 原生体验 + 固定 seed 的
确定性复现**。这四者组合目前没有看到成熟开源替代。

## 5. 典型使用场景

### 场景 A：复现提交后响应丢失导致的重复退款

用户声明「第一次退款在服务端提交成功，但响应超时」，图按重试策略再次调用。工具报告同一
退款单号产生两笔已提交退款，测试失败，并给出每次尝试的序号、状态与 checkpoint 归属。

### 场景 B：验证幂等键修复有效

同一场景下开启相同幂等键，模拟账本只有一笔退款，测试通过。若用户错误地让每次重试生成
不同幂等键，工具再次报错并指出键不一致。

### 场景 C：验证 Checkpoint 恢复安全

退款完成后进程中断，用户从 checkpoint 恢复。工具按 run/thread/checkpoint 归属 effect，
确认已完成的副作用没有被再次提交；若节点被整体重跑导致重复，则测试失败。

### 场景 D：验证 Interrupt 重放安全

图在人工确认处 interrupt。用户恢复后发现节点重跑；工具区分「副作用在 interrupt 之前/之后」
两种放置方式，明确哪种会重复、哪种安全。

### 场景 E：在 CI 中断言业务不变量

用户声明「本场景退款最多 1 笔、通知最多 1 次」，并加入自定义业务断言。所有不变量在断网
环境下稳定运行，单场景 5 秒内完成，可直接进入 CI。

## 6. 功能优先级

> 实现状态（截至 v0.14.0）：P0 全部实现，P1 全部实现，P2 已实现其中 4 项
> （多框架工具、异步/并发竞态检测、邮件/订单/库存模板、JUnit XML 报告）。

### P0（MVP 必须，缺一不可）

- 场景声明与 pytest 集成：一个场景对象 + 一行启用。
- Effect Store：记录类型、业务键、参数哈希、尝试序号、提交状态、run/thread/checkpoint。
- 提交后响应丢失（lost-ack）故障注入，固定 seed。
- 退款模拟服务（内存账本 + 幂等键开关）。
- `no_duplicate_effects` 不变量与可定位失败报告。
- 退款示例 + Quickstart 文档。

### P1（MVP 应有，可在 4 周内完成）

- 其余故障类型：提交前超时、连接重置、500、部分成功。
- Checkpoint 恢复与 LangGraph RetryPolicy 驱动。
- Interrupt 恢复场景。
- `max_effect_count` 与自定义 predicate。
- 跨测试隔离、确定性回归测试（20 次一致）。

### P2（发布后，按反馈排序）

- 更多框架适配器（CrewAI、OpenAI Agents SDK 等）。
- 异步/并发图的竞态检测。
- 持久化 Effect Store 与跨进程恢复。
- 更多内置模拟服务模板（邮件、订单、库存）。
- CLI / CI 报告格式（JUnit XML 等）。

## 7. 不做清单（MVP）

- 不做 LLM 输出质量评估、提示词评测、数据集管理。
- 不做生产监控、遥测、告警、流量录制回放。
- 不做 Web UI、云控制面、托管服务。
- 不做自动修复幂等性、自动改写用户图或工具。
- 不做并发/异步图竞态检测（仅串行图）。
- 不做跨进程持久化、分布式存储。
- 不调用任何真实支付、退款、邮件、数据库 API。
- 不假设竞品不存在；每次扩展前先复核替代方案。

## 8. 可量化验收标准（MVP 发布闸门）

> 状态（截至 v0.14.0）：AC-1、AC-4、AC-5、AC-7、AC-8 已由自动化验证覆盖；
> AC-2、AC-3、AC-6 已在示例测试与文档中覆盖，等待外部用户独立试用复核。

| 编号 | 标准 | 验证方式 |
|------|------|----------|
| AC-1 | 新用户按 Quickstart 在 10 分钟内跑通退款示例并看到失败报告 | 3 名未接触过项目的用户计时试用 |
| AC-2 | 四类路径（重试、Checkpoint 恢复、Interrupt、lost-ack）中至少三类能稳定复现重复副作用 | 示例测试 + 手工复核 |
| AC-3 | 无幂等键失败、有幂等键通过，结论清晰可辨 | 同一场景两套配置对比 |
| AC-4 | 同场景同 seed 连续 20 次结论与 effect 计数完全一致 | 自动化重复运行脚本 |
| AC-5 | 单场景本地无网络执行 <5 秒 | pytest 计时 |
| AC-6 | 3 名目标用户仅凭失败报告，2 分钟内指出重复 effect 与业务键 | 可用性测试 |
| AC-7 | 核心模块行覆盖率 ≥90% | coverage 报告 |
| AC-8 | 断网环境下全部测试通过，无真实外部请求 | CI 断网任务 |

## 9. 待验证假设与验证计划

| 假设 | 当前证据 | 验证方式 | 未通过时的应对 |

| H1：目标用户愿意为副作用安全单独写场景测试 | 间接：LangGraph issues 与官方幂等键建议 | 5 名目标用户访谈 + 3 人试用 Quickstart | 降低声明成本，改为装饰器/自动发现 |
| H2：重复副作用是高频真实痛点，而非理论风险 | 间接：issue #9240、#7417 等 | 访谈中收集真实事故案例 | 收窄场景，转向「恢复路径回归」 |
| H3：模拟服务的重试语义足够接近真实客户端 | 推断 | 用 2-3 种真实 SDK 行为对照测试 | 调整故障注入接缝与文档说明 |

## 10. MVP 成功判据

4 周 MVP 结束时，满足以下三条即视为产品假设初步成立：

1. 项目自身示例与测试全部通过发布闸门 AC-1 至 AC-8。
2. 至少 3 名外部目标用户独立完成 Quickstart，其中至少 1 人将其用于自己的 LangGraph 项目。
3. 至少收集到 1 个真实（可脱敏）重复副作用案例，能由本工具复现。

若第 2、3 条未达成，不扩功能，优先修正定位与使用门槛。
