# Feature Specification: HTTP 故障注入传输层

**Feature Branch**: `003-http-fault-transport`

**Created**: 2026-11-13

**Status**: Draft

**Input**: User description: "HTTP 故障注入传输层（httpx transport adapter）：编号 3，short name http-fault-transport。为真实 httpx.Client/AsyncClient 提供可选传输层适配器，在 transport 层注入确定性故障（lost-ack 等），无需改写业务代码；复用现有 EffectGuard 记账与 FaultPlan；离线确定性、无真实网络；httpx 为可选 extra，核心包仍仅标准库。"

## 背景与证据

- 已核实事实：现有 `EffectGuard` 只能包裹函数级副作用。用户若使用真实的 HTTP 客户端
  （如 `httpx.Client`），需要把每个业务方法逐一手工包装，或改写客户端调用代码，才能获得
  attempt 记账与故障注入。
- 已核实事实：HTTP 客户端天然提供了稳定的接缝——传输层（transport）。在传输层包裹可以
  同时覆盖 SDK、手写请求与第三方封装，且业务代码零改动。
- 合理推断：真实 Agent 项目中的写副作用大多经由 HTTP 客户端发出（退款、下单、发消息）。
  若不能在传输层注入 lost-ack，002 已支持的异步路径与 001 的重复检测很难直接用于真实项目。
- 证据来源：本仓库 `src/agentreplayguard/guard.py`、`src/agentreplayguard/faults.py` 的
  现有实现，以及 001/002 规格中「不要求用户改写业务图/业务代码」的既有契约。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 用真实同步 HTTP 客户端复现 lost-ack (Priority: P1)

用户的应用使用 `httpx.Client` 调用模拟的退款服务。他把客户端配置为使用本项目的传输层
适配器，并声明故障计划：第 1 次退款请求在服务端已提交后丢失响应。业务代码的重试逻辑再次
发送同一请求；场景结束时报告同一业务键存在两笔已提交退款，测试失败并给出定位信息。

**Why this priority**: 这是本特性的核心价值：不改业务代码即可在真实客户端上复现重复副作用。

**Independent Test**: 使用进程内模拟传输层（不联网）运行同步 lost-ack 示例，断言账本含
2 条 `committed` 的退款记录、attempt 为 1/2、业务键一致，且不变量检测失败。

**Acceptance Scenarios**:

1. **Given** 配置了适配器且无故障的客户端，**When** 发送一次已分类请求，**Then** 账本
   新增 1 条 `committed` 记录，且调用方拿到真实响应。
2. **Given** 同一业务键的第 1 次尝试被注入「提交后响应丢失」，**When** 调用方重试，
   **Then** 账本含 2 条 `committed` 记录，且第二次调用拿到真实响应。
3. **Given** 第 1 次尝试被注入「提交前失败」，**When** 调用方捕获客户端异常，**Then**
   账本记录 `not_committed`，底层传输层未被调用，重试后仅 1 条 `committed`。

---

### User Story 2 - 异步 HTTP 客户端同样可注入 (Priority: P1)

用户的 Agent 节点使用 `httpx.AsyncClient`。他使用异步版适配器，得到与同步版完全一致的
记账、故障语义与报告结论。

**Why this priority**: 002 已让异步路径成为一等公民；若 HTTP 接缝只支持同步，异步用户仍
无法使用该特性。

**Independent Test**: 使用进程内模拟异步传输层运行异步 lost-ack 示例，断言与同步示例相同
的记录数量、状态序列与 attempt 序号。

**Acceptance Scenarios**:

1. **Given** 异步客户端与已分类请求，**When** 正常 `await` 请求，**Then** 账本新增 1 条
   `committed` 记录并返回真实响应。
2. **Given** 同一故障计划，**When** 分别用同步与异步客户端执行等价场景，**Then** 两者
   effect 数量、状态序列与 attempt 序号一致。
3. **Given** 异步请求被取消，**When** 调用方捕获取消，**Then** 账本记录「结果未知」而
   不是已提交。

---

### User Story 3 - 业务键与幂等键从请求中提取 (Priority: P2)

用户不希望为每个调用点传参。他声明一个分类函数，从请求方法、URL 与请求体中提取副作用
类型、业务键、参与哈希的参数以及幂等键（请求头或 JSON 字段）。未匹配分类函数的请求
（如健康检查、只读查询）直接透传，不记账、不注入故障。

**Why this priority**: 没有提取策略，传输层无法把请求关联到业务语义，也无法区分读写。

**Independent Test**: 单元测试覆盖：从 JSON 体提取业务键、从幂等键头提取幂等键、未匹配
请求透传且账本为空、分类函数返回空业务键时快速失败。

**Acceptance Scenarios**:

1. **Given** 分类函数从 JSON 体提取业务键与幂等键，**When** 发送请求，**Then** 账本字段
   与函数级 guard 使用同一参数哈希口径。
2. **Given** 请求不被分类函数匹配，**When** 发送请求，**Then** 请求正常完成，账本无新增，
   故障计划不被消耗。
3. **Given** 分类函数返回空业务键或非法类型，**When** 发送请求，**Then** 快速失败并说明
   原因，不发起底层传输。

---

### User Story 4 - 故障映射为客户端可识别的异常 (Priority: P2)

用户的业务重试逻辑按客户端异常类型判断是否重试（如连接超时 vs 读取超时）。适配器注入的
故障应表现为该客户端的标准异常，而不是项目自定义异常，使现有重试策略原样生效。

**Why this priority**: 若异常类型不对，用户的重试逻辑不会触发，lost-ack 场景就无法被真实
复现。

**Independent Test**: 单元测试断言提交前故障表现为连接类超时异常、提交后故障表现为读取类
超时异常，且账本状态分别为 `not_committed` 与 `committed`。

**Acceptance Scenarios**:

1. **Given** 提交前故障，**When** 客户端发起请求，**Then** 调用方收到连接类超时异常，
   底层未被调用。
2. **Given** 提交后故障，**When** 客户端发起请求，**Then** 调用方收到读取类超时异常，
   但账本记录为已提交。
3. **Given** 未注入故障，**When** 底层传输层本身抛出异常，**Then** 账本记录
   `not_committed` 并原样传播该异常。

---

### Edge Cases

- **分类函数抛异常**：必须快速失败并说明是分类配置错误，不得吞掉后继续透传。
- **请求体不可解析**：分类函数自行决定如何取值；若参数不可序列化为规范 JSON，必须快速
  失败并指出不可序列化，不得记录未哈希的原文。
- **幂等键缺失**：允许为空；账本记录与函数级 guard 一致地留空，不推断默认值。
- **同一请求被重定向或重试**：每次实际传输层调用视为一次独立尝试，由业务键归组。
- **底层传输层不可用**（`httpx` 未安装）：核心包导入不得失败；只有显式使用适配器时才
  给出可操作的安装提示。
- **流式响应**：本次以响应头到达作为提交边界；流式响应体读取失败的语义不在范围内，
  文档必须注明该边界，且不得把响应体丢失记录为已提交的第二次尝试。
- **适配器被多个客户端共享**：账本与故障计划的消耗顺序仍由调用顺序决定，必须确定。
- **HTTP 客户端自身超时**：由客户端配置决定，适配器不引入真实延迟。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供可包裹同步 HTTP 客户端传输层的适配器，使现有业务代码无需
  改动即可获得 attempt 记账与故障注入。
- **FR-002**: 系统 MUST 提供对应的异步传输层适配器，语义与同步版一致。
- **FR-003**: 用户 MUST 能声明一个分类函数，从请求中提取副作用类型、业务键、参数映射与
  可选幂等键；参数哈希与幂等键哈希 MUST 与函数级 guard 使用同一口径。
- **FR-004**: 未匹配分类函数（返回空）的请求 MUST 直接透传给底层传输层，MUST NOT 记账、
  MUST NOT 消耗故障计划。
- **FR-005**: 已匹配请求的每次传输层调用 MUST 记录为独立尝试，包含 effect 类型、业务键、
  参数哈希、幂等键哈希、attempt、状态与逻辑时间；run/thread/checkpoint 归属 MUST 与当前
  场景上下文一致。
- **FR-006**: 故障注入 MUST 复用既有故障计划与消耗顺序；提交前故障 MUST 记录
  `not_committed` 且 MUST NOT 调用底层传输层；提交后故障 MUST 在底层成功返回后记录
  `committed`。
- **FR-007**: 注入故障向调用方呈现的异常 MUST 是 HTTP 客户端库的标准异常类型：提交前为
  连接类超时，提交后为读取类超时；MUST NOT 向调用方暴露项目内部故障类型。
- **FR-008**: 底层传输层抛出的异常 MUST 记录 `not_committed` 并原样传播，不得包装。
- **FR-009**: 异步传输层调用被取消时 MUST 记录「结果未知」并传播取消。
- **FR-010**: 分类函数返回非法业务键（空值或非字符串）或参数不可序列化时 MUST 快速失败，
  错误信息 MUST 指出配置问题，且 MUST NOT 发起底层传输。
- **FR-011**: HTTP 支持 MUST 作为可选 extra 提供；未安装该可选依赖时，核心包导入与现有
  功能 MUST 完全不受影响。
- **FR-012**: 适配器 MUST 能与任意符合客户端传输层接口的实现组合，包括进程内模拟传输层，
  以便测试离线运行。
- **FR-013**: 示例与测试 MUST 在无网络环境下运行，MUST NOT 发起真实网络请求、引入真实
  延迟或新增核心运行时依赖。
- **FR-014**: 现有函数级 guard、异步路径、报告结构与公开 API MUST 保持向后兼容。
- **FR-015**: 适配器 MUST 复用现有报告与不变量检测，用户无需学习第二套结论格式。

### Key Entities

- **HTTP Effect 描述**：分类函数从请求中提取的副作用语义，包含 effect 类型、业务键、
  参数映射与可选幂等键；不包含原始请求体持久化。
- **HTTP 传输尝试**：与既有 effect 记录同构，复用现有账本与去重口径，不引入新实体。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 同步与异步 lost-ack 示例均在 100% 的运行中检测出同一业务键的 2 条已提交
  记录并使测试失败。
- **SC-002**: 同一 seed 下，同步与异步等价 HTTP 场景的 effect 记录数、状态序列与 attempt
  序号 20/20 次完全一致。
- **SC-003**: 提交前故障时底层传输层调用次数为 0，账本已提交记录数为 0。
- **SC-004**: 未匹配请求 100% 透传且账本新增记录数为 0。
- **SC-005**: 未安装可选 HTTP 依赖时，全部现有测试通过且核心包导入成功。
- **SC-006**: 全部新增测试在断网环境下通过，单个典型场景完成时间小于 5 秒。
- **SC-007**: 核心模块行覆盖率保持不低于 90%，ruff 与类型检查无错误。

## Out of Scope

- 真实网络请求、真实第三方服务（支付、退款、消息平台）的写操作客户端。
- 流式响应体丢失、上传下载断点续传的语义。
- 请求签名、鉴权、重试策略的自动推导。
- 其他 HTTP 客户端（requests、aiohttp、urllib3）的适配器。
- 并发请求的竞态与线性一致性检测（沿用既有「不支持并行扇出」的范围）。
- 新增遥测或持久化原始请求/响应内容。

## Assumptions

- 用户使用的 HTTP 客户端库提供可替换的传输层接口，且错误类型可映射为连接类/读取类超时。
- 用户的分类函数能够仅依据请求本身（方法、URL、头、体）确定副作用语义；无法确定时应
  返回空以透传。
- HTTP 客户端库作为可选 extra 安装；核心包与现有示例仍不引入任何第三方运行时依赖。
- 所有测试使用进程内模拟传输层，不依赖真实网络、真实时钟或真实延迟。
- 传输层适配器与函数级 guard 共享同一 Effect Store、故障注入器与不变量，不引入第二套账本。
